# Skill: Module Card

> `_modules/project_modules.md`에 프로젝트 카드를 추가하거나 수정하는 절차

---

## 언제 이 스킬을 쓰는가

- 새 프로젝트 카드를 추가할 때
- 기존 카드의 내용이 부실해서 보강할 때
- 소스 문서(설계 문서, README, 이력서 기초 자료)를 카드로 정제할 때

---

## 카드 구조 (고정)

```
## N. 프로젝트명

**요약**
3~5문장. 배경 → 판단 → 방향.

**기술 스택**
핵심 스택만. 선택 이유가 있으면 함께.

**핵심 설계**
설계 결정들. 항목별 "무엇을 / 왜 / 어떻게"로 서술.

**트러블슈팅** (선택)
원인 특정 과정까지 포함. 핵심 설계와 성과 사이에 삽입.

**성과**
before/after 수치 또는 구조적 달성 내용.
```

섹션 순서는 고정. 트러블슈팅만 선택 섹션.

---

## 작성 절차

### Step 1. 요약 작성

아래 세 가지를 한 단락에 담는다:
- 왜 이 프로젝트가 시작됐는가 (문제 또는 동기)
- 어떤 판단을 했는가 (기술 선택 이유, 설계 방향)
- 어떤 방향으로 갔는가 (접근법의 핵심)

나쁜 예:
```
게임 데이터 관리 툴을 개발했습니다. Python과 PyQt5를 사용했습니다.
```

좋은 예:
```
엑셀 기반 공동 편집 환경에서 충돌이 조용히 데이터를 손실시키는 문제를
해결하기 위해 시작한 데스크탑 툴. 서버 지원 없이 단독으로 진행해야 하는
제약 하에 Python + PyQt5 선택 (데스크탑 앱 개발 용이, Pandas 기반 테이블
처리 적합). Python 경험 전무 상태에서 신규 스택 습득 후 적용.
```

### Step 2. 기술 스택 정리

포함 기준:
- 설계 결정에 영향을 준 것 (왜 이걸 선택했는가 설명 가능한 것)
- 핵심 설계 항목과 연결되는 것

제외 기준:
- 외부 도구 (예: HeidiSQL — DB 클라이언트일 뿐, 구현 스택 아님)
- 기본 내장이라 선택 여지가 없었던 것

버전은 선택 판단에 영향을 준 경우에만 기재.

### Step 3. 핵심 설계 항목 선별

각 항목은 아래 세 가지를 포함:
```
무엇을: 이 설계가 다루는 문제 또는 목표
왜:     이 방식을 선택한 이유
어떻게: 구체적인 구현 방식 (클래스명, 알고리즘, 흐름 등)
```

나쁜 예 (기능 나열):
```
- 3-way merge 충돌 해결 기능 구현
- 페이지네이션 엔진 구현
```

좋은 예 (설계 서술):
```
- 3-way Merge 충돌 해결: Source / Base / Target 세 버전을 나란히 비교하는
  Diff 뷰. ResolveNode / ResolveList로 행 단위 충돌 상태(Clean / Expired /
  Conflict) 추적. 충돌을 "인지 불가" 상태에서 "선택·해결 가능" 상태로 전환.

- GTDocPaginator: 수만 행 테이블을 Qt 위젯에 전체 로드 시 UI 응답 불량
  (30초+) → 페이지 단위 슬라이스 로딩으로 대체. 선택 행 기억 후 페이지
  전환 시 자동 스크롤 복원.
```

### Step 4. 트러블슈팅 항목 작성 (해당 시)

아래 네 요소를 반드시 포함:
```
문제:       어떤 증상이 있었는가
원인 특정:  어떤 방법으로 원인을 찾았는가 ← 이 부분이 핵심
해결:       무엇을 어떻게 바꿨는가
결과:       before/after
```

차별화 맥락이 있으면 명시:
- `팀 전체가 놓친 상태에서 단독으로 원인 특정`
- `기존 접근법과 다른 방향으로 접근해 해결`

### Step 5. 성과 작성

포함 기준:
- before/after 수치 (예: `UI 프리징 30초+ → 즉시 응답`)
- 구조적 달성 내용 (예: `PK 충돌 원천 차단`)
- 차별화 맥락 (예: `단독 원인 특정, 팀 미발견 상태`)

제외 기준:
- 기간·인원수 단독 나열
- "구현했다"는 사실 자체

## 소스 문서 유형별 매핑

| 소스 섹션 | 카드 섹션 |
|----------|----------|
| 프로젝트 개요 / 목적 | 요약 |
| 기술 스택 | 기술 스택 (제외 기준 적용) |
| 주요 기능 구현 | 핵심 설계 (설계 서술로 재작성) |
| 기술적 도전과 해결 | 트러블슈팅 또는 핵심 설계의 "왜" |
| 성과 및 규모 지표 | 성과 (수치 있는 것만) |
| 이력서 문구 예시 | 참고용 — 카드에 포함하지 않음 |
| README 아키텍처 다이어그램 | 핵심 설계 구조 설명으로 텍스트화 |
| 미구현 / 예정 항목 | 카드에 포함하지 않음 |

## 작성 완료 체크리스트

**요약**
- [ ] 왜 시작했는지 (문제/동기)가 있는가
- [ ] 기술 선택의 이유가 있는가
- [ ] 명사체로 작성했는가

**기술 스택**
- [ ] 실제 구현 스택만 포함했는가 (외부 도구 제외)
- [ ] 불필요한 버전 정보를 제거했는가

**핵심 설계**
- [ ] 각 항목에 "무엇을 / 왜 / 어떻게"가 있는가
- [ ] 기능 나열이 아닌 설계 판단으로 서술했는가
- [ ] 클래스명, 알고리즘, 흐름 등 구체적 근거가 있는가

**성과**
- [ ] before/after 수치 또는 구조적 달성 내용이 있는가
- [ ] 기간·인원수 단독 나열이 없는가
- [ ] "구현했다"는 사실 자체만 쓴 항목이 없는가

---

## 주의사항

- `project_modules.md`를 수정할 때는 반드시 사용자에게 변경 내용을 먼저 확인받는다.
- 카드 번호(N.)는 기존 순서를 유지한다. 삽입 시 뒤 번호를 밀어낸다.
- 소스 문서에 없는 내용은 추가하지 않는다.
